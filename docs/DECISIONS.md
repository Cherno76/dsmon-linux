# 决策记录

日期：2026-11-07。后续调整请追加新条目，不要改写已有决定的理由。

## D1 新建项目，不 fork macOS 版

- 状态：已定
- 背景：源项目约 20.3k 行 Swift，42 个 UI 文件全部依赖 SwiftUI/AppKit/Charts；Core 还依赖
  Network、CFNetwork、CoreAudio。用 `#if os(Linux)` 逐文件切会把代码变成两套。
- 决定：在 `/home/cherno/项目/dsmon-linux` 新建 Go 项目，只复用数据格式、规则和测试意图。
- 后果：Swift 代码不进入新仓；每个源文件的处置见 `docs/PORTING.md`。

## D2 语言：Go

- 状态：已定
- 备选：Rust（ratatui 画曲线更强，但整体工期约多 20–40%，编译慢）、Swift（Arch aarch64 无官方
  工具链支持，Linux 上 TUI 生态弱）。
- 决定：Go 1.24+。
- 理由：`net/http` + `httputil.ReverseProxy` 覆盖流式代理的主要难点；单静态二进制；编译快；
  bubbletea/lipgloss 足够做 btop 风格界面。
- 后果：盲文曲线需要自己写渲染器（约 100–200 行），不引第三方图表库。

## D3 界面：TUI，不是 GUI

- 决定：全屏 TUI，跑在 foot/kitty 里，布局模仿 btop：顶部指标卡、中部图表与表格、底部快捷键提示。
- 理由：用户明确要“窗口中跑的类似 btop 那样的显示”；TUI 开发快、远程可用、无 GUI 工具链风险。
- 后果：不引入 GTK/Qt；窗口管理、透明、字体都由终端负责。

## D4 去掉刘海，但保留两张曲线

- 决定：侧边刘海、菜单栏、呼吸灯、图标动画、庆祝烟花全部不做。
- 活动曲线（20 格 × 6 秒）和流量曲线（60 格 × 1 秒，上下行双泳道）必须实现，
  放在 TUI 的“实时”面板里，规格见 `docs/CURVES.md`。
- 理由：曲线提供“刚刚发生了什么”的即时信息，是用户明确点名要保留的部分。

## D5 去掉余额对账与盗刷检测

- 决定：不实现 `BalanceAudit`、`SpendDrainRule`、`SpendAlertLifecycle`、放行/静音流程、
  15 分钟滑窗、安静时段、待结算差额、最大音量报警。
- 余额仍要查询和显示，但只作为信息：数字、曲线、失败原因，不参与任何判定。
- 理由：用户明确说“对账/盗刷不做”；这块逻辑最绕、最容易误报，砍掉能显著缩小范围。

## D6 余额与告警的边界

- 保留：余额接口调用、60 秒轮询、`balance_sample` 入库、TUI 余额卡与趋势线。
- 可选：低于阈值时把余额文字变黄（默认开），不弹窗、不响铃、不发通知。
- 不保留：24h 残差、外部消费推断、Level 3 警报、系统通知冷却。

## D7 daemon 与 TUI 分进程

- 决定：
  - `dsmon serve` 常驻，负责代理、采集、余额轮询、计费更新检查。
  - `dsmon tui` 通过 `$XDG_RUNTIME_DIR/dsmon.sock` 取实时数据；历史查询可只读打开数据库（WAL）。
  - `dsmon settings` 写配置文件，然后通过 socket 通知 daemon 热加载。
- 理由：TUI 崩了不能停代理；曲线数据只在 daemon 内存里，必须由 daemon 提供。
- 协议：换行分隔 JSON，详见 `docs/ARCHITECTURE.md`。

## D8 数据库与 macOS 版同构

- 决定：`usage_log` / `meta` / `balance_sample` / `pricing_revision` 的表名、列名、索引、
  默认值保持一致，见 `internal/store/schema.sql`。
- 后果：Mac 版 `usage.db` 可直接 `dsmon import`；计费规则时间轴和费用不会因为换平台而重算。
- 任何 schema 变更都要写迁移，并在 `docs/ARCHITECTURE.md` 记录。

## D9 路径遵循 XDG

| 用途 | 路径 |
|---|---|
| 配置 | `~/.config/dsmon/config.toml` |
| 数据 | `~/.local/share/dsmon/usage.db` |
| 状态/日志 | `~/.local/state/dsmon/` |
| 运行期 socket | `$XDG_RUNTIME_DIR/dsmon.sock` |
| 加密密钥 | `~/.local/share/dsmon/enc_key`（0600） |

## D10 计费更新保留人工确认

- 决定：抓页面 → 提纯文本 → 调模型转成规则 → 显示差异与体检 → 用户确认 → 按生效日期导入。
- 7 天自动检查一次；发现更新只标记“待确认”，绝不自动写 `pricing_revision`。
- 理由：模型会自信地编出过期价目表；这是源项目验证过的坑。

## D11 设置是 TUI，Hyprland 快捷键打开

- 决定：`dsmon settings` 是一个表单式 TUI；在 `~/.config/hypr/bindings.lua` 加 `o.bind(...)`，
  用浮动 foot 窗口打开。
- 修改 Hyprland 配置时按 omarchy skill 的规则来；改完 `hyprctl reload`。
- 先不做 GUI 设置；以后要加 GTK4 窗口不影响 daemon。

## D12 通知与声音

- 系统通知走 `notify-send`（Quickshell 接 `org.freedesktop.Notifications`）。
- 默认不播放声音；需要时用 `pw-play` 播一个短音，不做“最大音量持续报警”。
- 通知只用于：代理启动失败、端口占用、计费更新待确认。

## D13 依赖策略

- 允许：
  - `github.com/charmbracelet/bubbletea`、`lipgloss`、`bubbles`
  - `modernc.org/sqlite`（纯 Go，避免 cgo）
  - `golang.org/x/net/html`（计费页面提取）
  - `github.com/BurntSushi/toml`（配置）
  - 标准库 `crypto/aes` + `crypto/cipher`（密钥加密）
- 需要论证后才能加：任何图表库、Web 框架、ORM、日志框架。
- 不引入：cgo 版 SQLite（除非 modernc 性能成为问题）、任何运行时。

## D14 文案与注释

- 标识符、包名、提交 subject 用英文；注释和文档用中文。
- 界面文案先做中/英两套最小集合，不逐条移植源项目的 400+ 条 `Strings`。

## D15 代码风格

- `gofmt` + `go vet` 必须干净；错误用 `fmt.Errorf("...: %w", err)` 包装。
- 单一写库者：所有写操作进一个 goroutine + channel，避免 `SQLITE_BUSY` 和锁竞争。
- 纯逻辑（时间轴、缩放、曲线桶）必须可单测，不碰终端和网络。

## D16 固定 SQLite 驱动版本以维持 Go 1.24 下限

- 决定：使用 `modernc.org/sqlite v1.44.3`，不跟随到需要 Go 1.25/1.26 的新版本。
- 理由：项目声明 Go 1.24+；`modernc.org/sqlite` 从 v1.46 起要求 Go 1.25，最新版要求 Go 1.26。
- 后果：升级驱动时必须同步评估并提升 `go.mod` 的 Go 下限；不要在未说明的情况下 `go get -u`。

## D17 import 采用“新库复制、旧库合并”

- 决定：
  - 目标库不存在：先复制源库到临时文件并校验，再原子 rename 到目标路径，之后补列/建索引。
  - 目标库已存在：按 `pricing_revision.fingerprint` 复用已有修订并重映射行号；用量走唯一索引
    `INSERT OR IGNORE`，余额样本按四元组去重。
  - 合并路径给无 UUID 的用量行生成稳定 fallback UUID；无 UA 的旧行留给启动维护按 endpoint
    反推客户端。
- 理由：首次导入要尽量保留 Mac 库原貌和费用；重复导入或并入日常库必须幂等，不能重复计费。
- 后果：同一份源库重复导入时 inserted 为 0；目标库已有的同语义行不会被覆盖，历史费用保持原值。
  源库只读，WAL 中尚未 checkpoint 的数据也会被纳入。

## D18 代理用手写 Handler，不用 ReverseProxy

- 决定：`internal/proxy` 使用 `http.Handler` + `Transport.RoundTrip`，不用 `httputil.ReverseProxy`。
- 理由：一次请求要同时完成严格路由、超限拒绝、鉴权覆盖、SSE 分块 flush、压缩旁路分析和
  结束时单条落库；`ReverseProxy` 的钩子会让这些状态散在 `ModifyResponse` / `ErrorHandler` 里，
  不如显式请求生命周期可靠。
- 后果：请求体会先按 20MB 上限读入，再原样发给上游；chunked 客户端请求也能接受，但上游看到的是
  明确的 Content-Length，不再是客户端原来的分帧。

## D19 压缩字节原样透传，分析走旁路

- 决定：上游 `Transport` 固定 `DisableCompression=true`；不移植 Mac 版 URLSession 自动解压后
  再剥 `Content-Encoding` 的平台取巧。客户端收到的是上游原始压缩字节和原始头。
- 用量分析把响应分片另喂给 gzip/deflate 解压器，再进入 `ResponseBodyCollector`；因此不会为了
  统计 token 改写转发内容。`br` 没有加入第三方解码依赖，只透传不分析。
- 回归：集成测试同时断言 gzip 字节、`Content-Encoding`、`Content-Length` 不变，以及 usage 仍落库。

## D20 Phase 2 密钥只从环境变量注入

- 决定：`dsmon serve` 从 `DSMON_API_KEY` 或 `DEEPSEEK_API_KEY` 读取 key，不读取 TOML、不写盘。
- 理由：设置页的 AES-GCM 配置尚未实现；先落地明文配置会把硬约束变成一次需要迁移的债务。
- 后果：当前启动必须显式导出 key；守护进程的环境文件由 systemd 阶段再设计，仍不得提交进仓库。

## D21 余额 URL 默认派生，采样写失败保留已查询余额

- 决定：`DSMON_BALANCE_URL` 未设置时取 `DSMON_OPENAI_BASE` 去掉尾部斜杠再加 `/user/balance`。
- 决定：余额查询成功但采样落库失败时，轮询器仍更新内存快照并把错误标为 `storage`，
  不把界面余额退回上一次成功写入的旧值。
- 理由：余额数字已经由上游返回，落库失败是持久化问题，不应伪装成查询失败；但错误仍要暴露给
  TUI，方便发现磁盘或数据库故障。
- 后果：TUI 需要同时显示余额值和 storage 错误；失败退避仍会继续，直到写入恢复。

## D22 用 klauspost/compress 旁路解压 zstd

- 背景：opencode 2.x 请求会带 `Accept-Encoding: zstd`，DeepSeek 返回
  `Content-Encoding: zstd` 的 SSE；只支持 gzip/deflate 时响应能正常转发，但 usage 提取失败，
  用量不会落库。
- 决定：加入 `github.com/klauspost/compress v1.19.2`，只在分析旁路解 zstd；转发路径仍保持
  上游压缩字节和 `Content-Encoding` / `Content-Length` 不变。
- 理由：选择 go 1.24 兼容版本；这是纯 Go 解码器，不引入 cgo。与“删掉 zstd 协商再让上游改发
  gzip”相比，不改变客户端与上游的压缩语义，也不简化代理规则。
- 后果：`br` 仍然只透传不分析；新增 zstd SSE 回归测试，断言压缩字节不变且 usage 落库。

## D23 TUI 通过 daemon IPC 取实时数据，渲染器保持纯字符串

- 决定：`dsmon tui` 用 bubbletea 全屏界面，通过 Unix socket 的 `stats` / `trace` /
  `series` / `requests` / `pricing` 命令取数；daemon 断线时界面继续显示并以错误状态提示。
- 决定：余额 24h/7d 趋势由 daemon 从 `balance_sample` 下采样成固定桶（24h 48 点、7d 28 点），
  结果缓存 30 秒，避免 TUI 每秒刷新时重复扫 7 天样本。
- 决定：渲染层只生成固定宽高的字符串矩阵，颜色由 lipgloss 在最后一步叠加；测试用
  `NO_COLOR` 路径断言每行宽度和总行数。Braille 不可用时回退到块字符。
- 理由：曲线帧只存在 daemon 内存里，TUI 崩溃不能影响代理；固定矩阵让 40/80/200 列和
  空库、单条请求、断线等状态都可回归测试，不依赖真实终端。
- 后果：`dsmon tui` 不直接写数据库；历史查询也走 daemon。Phase 5 的设置页仍复用同一个 IPC
  边界，但需要新增 `reload` 命令。

## D24 systemd 用户服务使用加密凭据与 linger

- 决定：常驻单元放在 `~/.config/systemd/user/dsmon.service`，key 用
  `systemd-creds encrypt --user --name=dsmon-api-key` 加密到
  `~/.config/dsmon/api-key.cred`（0600），unit 通过
  `LoadCredentialEncrypted=dsmon-api-key:...` 注入 `$CREDENTIALS_DIRECTORY`。
- 决定：`config.loadAPIKey` 的顺序是环境变量优先，其次读取 systemd 凭据；环境变量方便
  临时排障，systemd 凭据用于日常常驻。`loginctl enable-linger` 让用户未登录时服务仍运行。
- 理由：硬约束要求密钥不落明文；加密凭据由 systemd 管理，不需要在仓库或 shell profile
  里保存 key。linger 是 `systemd --user` 在无图形会话时继续运行的必要条件。
- 后果：重装二进制后需 `systemctl --user restart dsmon.service`；迁移机器时凭据文件不能直接
  跨 host 复用，必须重新加密。D20 的“只从环境变量读取”由本条目扩展为环境变量 + systemd
  凭据，历史条目保留不改写。

## D25 配置使用受控 TOML 子集，不引入通用 TOML 依赖

- 背景：Phase 5 需要稳定读写固定配置字段。本机拉取 `BurntSushi/toml` 时网络超时，直接访问
  GitHub 也出现 SSL EOF；不能让配置功能卡在外部依赖上。
- 决定：在 `internal/config/settings.go` 实现固定 section/key 的 TOML 子集解析与写入，
  只支持 `[proxy]`、`[balance]`、`[storage]`、`[pricing]` 下的单行 `key = value`。
- 理由：字段集很小，受控解析器可以继续使用标准库，并明确拒绝数组、内联表、多行字符串、
  未知字段和重复 key；错误信息可以直接面向中文用户。
- 后果：这个解析器不是通用 TOML，手工配置文件必须遵守 README 中的子集格式。新增字段时
  必须同步 `applySettingValue`、`marshalSettings`、默认值和测试。未来若能稳定引入依赖，
  可以整体替换解析器，但必须保留损坏配置不覆盖原文件的回归测试。

## D26 API key 使用 AES-GCM 配置密文，并定义三级优先级

- 决定：`dsmon settings` 用 32 字节随机密钥加密 API key，AES-GCM 密文写为 `v1:<base64>`；
  密钥存在 `~/.local/share/dsmon/enc_key`，密钥和配置文件权限都是 0600。
- 决定：key 来源固定为 `DSMON_API_KEY` / `DEEPSEEK_API_KEY` → 配置中的 `api_key_enc` →
  systemd `$CREDENTIALS_DIRECTORY/dsmon-api-key`。环境变量只用于临时排障。
- 决定：设置页只显示固定长度掩码；留空保存保留旧密文，输入新 key 才替换密文。配置保存和
  key 加密都失败时不会覆盖原文件。
- 后果：迁移机器必须同时迁移 `config.toml` 和 `enc_key`，否则只能从环境变量或 systemd
  credential 重新提供 key。D24 的 systemd 凭据继续有效，但降为第三优先级。

## D27 reload 使用配置快照与多代运行时

- 决定：同端口 reload 调 `proxy.Server.Reconfigure`，每个 HTTP 请求在开始时抓一份配置快照；
  不重启 listener，因此活动 SSE 和 keep-alive 连接不会被 reload 切断。
- 决定：端口变化时先绑定新 listener、启动新代理代与余额轮询，成功后再切换当前代并异步停止旧代；
  失败则旧代继续服务。SQLite store、写 goroutine 和 IPC socket 在整个 reload 过程中不重建。
- 决定：保留天数通过 `Store.SetRetentionDays` 进入已有写 goroutine，并在切换时立即清理一次。
- 理由：重开 SQLite 会丢队列/增加锁风险，重建 IPC 会让正在返回的 `reload` 响应丢失；把
  listener 和 store 的生命周期分开，才能同时满足热加载与单一写库者约束。
- 后果：同端口 reload 保留曲线和连接状态；改端口会启用一代新的代理曲线（旧代仍会把在途请求
  处理完）。reload 的预校验错误会原样显示在设置页。

## D28 TUI 功能分区使用 btop 风格标题边框

- 决定：TUI 渲染器提供统一的面板封装，顶部边框嵌入分区标题（Unicode 为
  `┌─┤ 标题 ├────┐`，ASCII 回退为 `+-[ 标题 ]----+`），账户、曲线、列表、详情和说明分别
  占独立面板。
- 理由：边框让余额、活动、流量、请求和计费信息在同一屏上更容易快速定位；统一封装可以保证
  窄屏、颜色和 ASCII 回退路径继续生成固定宽高的字符串矩阵。
- 后果：新增 TUI 分区时必须复用面板封装，并保留 40/80/200 列及 ASCII 回退的宽度/高度回归
  测试。

## D29 Omarchy 状态栏入口使用本地 bar-widget

- 决定：提供可选的用户级 `cherno.dsmon` Omarchy bar-widget，放在
  `~/.config/omarchy/plugins/`；点击图标执行
  `omarchy-launch-or-focus-tui --app-id=dsmon-dashboard dsmon tui`。
- 决定：入口只负责打开或聚焦 TUI，不把 TUI 嵌入状态栏，也不在栏内展示实时指标。
- 理由：复用 Omarchy 自带栏和窗口启动逻辑，不需要额外常驻 GUI；应用 ID 固定为
  `dsmon-dashboard`，重复点击不会开多个仪表盘窗口。
- 后果：该入口是 Linux 桌面的可选集成，不是 D4 所述 macOS 菜单栏的移植；依赖 Omarchy 与
  `dsmon` 在 `PATH` 中。安装步骤见 README，栏布局由用户的 `shell.json` 决定。

## D30 流量面板按 btop 双道填充绘制

- 决定：流量面板改成下载在上、上传在下的两条 btop 风格填充曲线，两条道各自使用独立量程；
  每条道首行叠加 `↓/↑` 与当前速率，不额外占行。内部高度按两条道均分，奇数行优先给下行。
- 理由：原实现把整个面板高度先交给下行，上行结果被渲染器裁掉，实际只显示一条曲线。btop
  的上下双道布局能在固定面板高度里同时看到两个方向，箭头与速率也消除了对标题数字的依赖。
- 后果：`docs/CURVES.md` 原先“两条折线、不填充”的绘制规则由本条目取代；数据口径、桶、
  量程和速率语义不变。ASCII 回退仍使用两条 sparkline。

## D31 流量曲线用 0.5 秒桶对齐 btop 点密度

- 决定：流量环改为 120 个 0.5 秒桶，保持 60 秒窗口；速率仍取最近 2 秒，不随桶宽缩短。
  IPC 的 `traffic_bucket_seconds` 改成浮点秒，以表达 0.5 秒桶。
- 理由：盲文画布每字符有 2×4 个点；原先 60 个 1 秒样本铺到约两倍字符数的画布上会依赖
  插值，细节不如 btop。btop 每个盲文字符承载两个相邻样本，120 个桶才能在同屏接近这种密度。
- 后果：流量曲线在同样的 60 秒窗口内更细、更接近 btop；活动曲线仍是 20 个 6 秒桶，因为
  它记录的是离散请求事件，不能靠提高采样频率凭空增加信息。

## D32 网格线使用半密度盲文点

- 决定：活动曲线的竖网格与流量曲线的横竖网格都改为每隔 2 个盲文点打一个点，不再使用
  3 或 4 点的稀疏步长。
- 理由：盲文单元本身只有 2×4 个点，间隔 4 点会按字符形成明显断点；间隔 2 点能在不把网格
  画成实心亮条的前提下接近连续线。
- 后果：网格更细，但仍能与数据填充区分；网格仍只占一个点列，不会重新出现“双竖线”。

## D33 TUI 面板改用 btop createBox 边框与栏目配色

- 决定：面板顶部边框按 btop `createBox` 的形状绘制为 `╭─┐标题┌────╮`，底部为
  `╰────────╯`；ASCII 回退为 `+-+标题+----+`。标题嵌在上边框内，标题文字与边框分开着色。
- 决定：沿用当前 Omarchy btop 主题的 Tokyo Night 配色。账户/内存用绿 `#9ece6a`，
  活动/CPU 用紫 `#ad8ee6`，流量/网络用粉 `#f7768e`，请求/进程用蓝 `#7aa2f7`；
  标题统一为 `#a9b1d6`，正文弱化为 `#565f89`。
- 理由：btop 的圆角框和栏目专属边框色比 D28 的旧式 `┌─┤ 标题 ├` 更紧凑，标题不额外占行；
  同一套色义也让账户、曲线、流量、请求四类信息在窄屏和宽屏下都能快速区分。
- 后果：D28 中的标题边框形状由本条目取代；新增面板必须传入对应的 `toneBox*`，并保留
  Unicode/ASCII 两种回退的边框回归测试。`docs/CURVES.md` 的布局示例同步更新。

## D34 网格线改为逐盲文点绘制

- 决定：活动曲线和流量曲线的横竖网格都从“每隔 2 个盲文点”改为逐点绘制。竖网格每格
  包含完整 4 个点（`⡇` 或 `⢸`），横网格每格包含同一行的左右 2 个点。
- 理由：在相同缩放比例下对照 btop，btop 的低流量曲线和网格点列仍占满一个盲文单元的四行；
  D32 的半密度画法在终端里仍显得有规律地断开，和 btop 的密点列观感不一致。
- 后果：网格更密但仍只占一个点列/点行，不会变成双线；网格与填充数据一样使用当前曲线色，
  因此不再表现出“稀疏大空隙”。`docs/CURVES.md` 的网格规则同步更新。

## D35 余额趋势改用单行盲文面积图

- 决定：账户面板的 24h/7d 趋势从块字符 sparkline 改为单行盲文面积图。每条趋势独立计算
  min/max，按终端的 2×4 点单元绘制，宽度 24 时得到 48 个横向点列。
- 理由：趋势和其他曲线现在使用同一种盲文点阵语言；相比 `▁▂▃▄▅▆▇█`，同样宽度下横向
  采样密度翻倍，趋势的拐点更清楚，也不再与活动/流量图的字形风格割裂。
- 后果：趋势只占原来的高度和宽度，不改变账户面板布局；`--ascii` 与 `NO_COLOR=1` 仍回退到
  块字符。新增盲文/块字符回退和宽度回归测试，`docs/CURVES.md` 补充余额趋势规则。

## D36 余额趋势按高度使用粉红→黄→绿渐变

- 决定：余额 24h/7d 趋势的每个盲文格按该格最高点列的归一化高度着色，低值为粉红
  `#f7768e`，中值为黄 `#e0af68`，高值为绿 `#9ece6a`，中间做 RGB 线性插值。
- 理由：单色点阵只能看出形状，不能快速分辨高低；沿用账户面板的 btop 色义，用绿表示较高余额、
  粉红表示较低余额，与余额低阈值已有的黄色提醒一致。
- 后果：TUI 渲染层新增“一行多段颜色”能力，趋势标签仍用普通正文色；ASCII/无颜色模式不参与
  渐变。两个趋势系列各自按自己的 min/max 映射，新增渐变端点和宽度回归测试。

## D37 余额趋势直接标注时间轴与余额量程

- 决定：趋势行从 `趋势 24h … 7d …` 改为 `余额 24h <min>–<max> … 时间→`，24h/7d 分别显示
  自己的余额范围；宽度不足时依次省略量程和 `时间→`，但不改变“左旧右新、低值在下”的语义。
- 理由：盲文面积图加渐变后，仅靠形状和颜色无法判断横轴方向与纵轴数值；直接标注比把说明
  藏在帮助页更有效，也不会改变趋势只占一行的布局。
- 后果：趋势行宽度会按终端宽度重新分配，典型 77 列下仍能同时显示两个量程和时间箭头；
  空趋势显示 `余额  24h --  7d --`。新增轴标签和窄屏截断回归测试。

## D38 用量页明确时间×tokens坐标并横向铺满

- 决定：用量趋势标题显示 `横轴 时间→ · 纵轴 tokens 0–<max>`。横轴固定为左旧右新的时间桶，
  纵轴为该时间列的总 tokens，堆叠所有模型或客户端。
- 决定：柱状图不再只画 `min(桶数, 宽度)` 列，而是始终画满面板可用宽度；桶数少时重复时间桶，
  桶数多时合并相邻桶。纵轴上限取实际渲染列合计值的最大值。
- 理由：旧实现确实按时间分桶、按 tokens 计高，但柱子只占左侧且没有轴标签，容易让人误以为
  横轴是模型或时间被压缩。铺满宽度后，时间从左到右的推进才与用户预期一致。
- 后果：长时间自定义范围发生桶合并时，每个渲染列代表多个时间桶，纵轴量程也按合并后的合计值
  计算，避免柱子超过图表顶部。新增轴标签、铺满宽度和渲染列量程回归测试。

## D39 用量柱状图显式标注纵轴向上

- 决定：用量趋势标题从 `纵轴 tokens 0–<max>` 改为 `纵轴 tokens ↑ 0–<max>`，明确 0 在底部、
  最大值在顶部，柱形从底边向上生长。
- 理由：实现虽然没有把 y 轴画反，但只写范围仍容易被理解成“从上往下读”；上箭头与横轴的
  `时间→` 一起给出明确方向。
- 后果：不改任何柱高计算或量程逻辑，仅改善坐标可读性并同步轴标签回归测试。

## D40 修正用量柱状图的纵轴填充方向

- 问题：D39 只把标题改成 `↑`，但 `appendUsageChart` 仍按 `height-row-1` 计算下边界；在从上到下
  输出时，这会让柱子从顶部向下长，和标签及文档描述相反。
- 决定：下边界改为 `row/height`，上边界改为 `(row+1)/height`。输出行仍按终端从上到下，
  但数值 0 对应最后一行，最大值对应第一行；半量程柱子只填下半部分。
- 理由：图表方向必须由实际几何计算保证，不能靠标题文字补救；该错误会被“50% 柱只填底部
  两行”的直接回归测试挡住。
- 后果：用量页柱形现在真正从底边向上生长；D39 的方向说明保持，补齐实现修正与测试。

## D41 用量柱状图直接绘制坐标轴

- 决定：不再只在标题里写 `横轴/纵轴`，而是在图表主体左侧绘制纵轴、在底部绘制横轴。纵轴
  标出最大值、约 50% 和 `0` 三个刻度；横轴画 `└─┬→`，并在下方标出左端、中点、右端的实际
  时间。小时桶用 `15:04`，天桶用 `01/02`，区间恰在次日零点结束时用 `24:00`。
- 理由：文字声明和实际图形分离时，用户仍需自己猜哪个方向是时间、哪个方向是 tokens；坐标轴
  画进图里后，方向与刻度可以直接由图形验证，窄屏也能保留至少两端时间标签。
- 后果：图表主体宽度扣除纵轴标签区，柱子仍铺满剩余绘图区；`--ascii` 回退为 `+ | - >`。
  回归测试改为按屏幕从上到下检查 50% 柱只填底部，并新增小时/天横轴标签与标签宽度测试。

## D42 纵轴宽度按全部刻度标签计算

- 问题：D41 只用顶部最大值的文本宽度预留纵轴空间。最大值显示为 `1.6M`（4 列）而中点为
  `799.2K`（6 列）时，`fmt` 会把较长的中点标签完整输出，导致该行 `┤` 和柱子整体右移。
- 决定：纵轴宽度取顶部、中点、底部三个刻度文本的最大显示宽度，再据此计算绘图区宽度。
- 理由：刻度行必须共用同一根竖轴；只按最大标签预留会在“最大值短、半值长”的组合下错位。
- 后果：所有刻度行的轴线列固定一致；新增直接检查每行 `┤/│` 列位置的回归测试。

## D43 用量柱体改用盲文点阵并按高度绿黄红渐变

- 决定：用量柱体从块字符 `█▓▒░…` 改为盲文点阵 `⣿⠿⡿⢿⣷⣾⣻⢾`，单系列使用 `⣿`，堆叠系列
  使用不同点阵区分；底部图例同步使用相同标记。柱体颜色按屏幕纵轴高度映射为绿 `#9ece6a`
  → 黄 `#e0af68` → 红 `#f7768e`。
- 理由：块字符让柱体看起来像实心色块，和已经使用盲文点的趋势/活动图不一致；点阵能保留
  btop 风格的细密质感。按绝对高度着色后，同一行颜色稳定，柱越高越接近红色，趋势比单色柱更
  直观。
- 后果：颜色不再按系列固定，系列改由点阵纹理区分；`--ascii` 仍回退为 `#*+=-~.:`。新增
  渐变端点、行高着色和点阵字形回归测试。

## D44 用量范围固定为六项并补齐自然日/自然月

- 决定：查询范围固定显示 `1今日 2昨日 3近7天 4近30天 5本月 6上月`，不再显示或接受第 7 项
  自定义范围；今日扩展到次日 0 点，本月扩展到下月 1 日。daemon 查询后使用
  `FillSeriesGaps` 给完整时间域内缺失的桶补 0，包括尚未发生的未来桶。
- 理由：范围选项直接写明比窄屏下的“1–7 切换”更容易扫描；日历区间应保持固定形状，今日始
  终为 24 小时、本月始终为当月天数，不能因为查询时刻靠前而缩短横轴。
- 后果：今日返回 24 个小时桶，本月返回当月天数；未来桶数值全为 0，绘图逻辑不需要识别
  “未来”或自行补桶。`store.AllUsagePeriods` 只保留六项，自定义区间仍仅作为 IPC 兼容路径。

## D45 天桶横轴末端显示最后一天而非下月边界

- 问题：D44 把本月扩展为 `[11/01, 12/01)` 后，天桶横轴右端直接格式化 `ToUnix`，截图显示
  `12/01`，容易让人误以为图表包含 31 天。
- 决定：天桶且终点恰为零点时，右端标签回退到 `To - 1 天`；整月显示 `11/30`，整段自定义
  日区间也显示最后一天。小时桶继续使用 `24:00` 表示次日零点边界。
- 理由：横轴标签应描述最后一个数据桶，而不是半开区间的排他边界；这样与“本月补齐当月
  天数”的语义一致。
- 后果：绘图与补零逻辑不变，只修正天桶末端标签；新增整月端点回归测试。


## D46 流量面板整体对齐 btop Net

- 决定：概览页流量区按 btop `Net::draw` 重做：下载在上半区、上传在下半区，共用一块盲文画布和
  一条公共中线；左侧保留各自量程，右侧放一个居中的 27 列统计框（窄屏 19 列），上边框嵌
  `download`、下边框嵌 `upload`，显示速率、bit 速率、`Top` 和 `Total`。
- 决定：流量图不再画 30 秒竖向网格，只保留公共中线；活动图的 60 秒竖网格不变。
- 决定：单位直接采用 btop `floating_humanizer` 的 IEC/bit 规则与整数移位口径；`Top` 是进程内
  最高 0.5 秒桶速率，`Total` 是 daemon 启动以来累计正文流量。
- 理由：用户要求流量部分直接抄 btop Net。此前“上下两条独立车道 + 每道各自标签”的布局仍像
  dsmon 自己的曲线，统计信息也被拆成两个小框；对齐 btop 后，方向、量程、速率和累计量在同一
  视觉块里可一眼对照。
- 边界：只移植绘制和统计语义，不引入 btop 的网卡选择、`auto/sync/zero` 控件，也不把数据源从
  代理正文字节改成系统网卡流量；dsmon 的流量仍只统计代理请求的上传/下载正文。
- 后果：`RenderTrafficNet`、`Trace` 的 `Top/Total` 字段和 IPC 协议一起扩展；`--ascii` 仍保留
  原有上下两条 sparkline 回退。新增单测检查镜像画布、单条基线、居中统计框和 btop 单位截断。

## D47 活动与流量并排，流量渐变取当前 btop 主题

- 决定：概览页在内容宽度 ≥60 列时把活动面板和流量面板左右并排，各占 `(width-1)/2` 列，中间
  留 1 列；窄于 60 列才回退为原来的上下堆叠。并排后两个面板共享整段图表高度，流量面板在半高
  窗口里也能显示完整的速率、Top 和 Total。
- 决定：流量渐变不再使用自定义蓝紫/紫粉，改为读取当前 Omarchy btop 主题的实际颜色：下载
  `#e0af68 → #f7768e → #f7768e`，上传 `#9ece6a → #449dab → #7aa2f7`；颜色仍按纵向高度映射，
  与 btop `Draw::Graph` 的渐变下标一致。
- 理由：上下堆叠时流量面板经常只有五六行，统计框只能显示速率；并排让高度变成两者共用，直接
  解决用户看到的 Top/Total 缺失。颜色也必须跟 btop 当前主题一致，而不是继续用另一套近似色。
- 后果：两个面板用独立子渲染器生成后按行拼接，父渲染器新增 raw 行支持；并排宽度不足时自动
  退回堆叠。新增并排标题同行的布局测试和 btop 渐变端点测试，`--ascii` 回退保持原样。

## D48 活动曲线改用 Catmull-Rom 平滑插值

- 决定：活动图在相邻 6 秒桶之间不再线性连接，而是用相邻四个桶做 Catmull-Rom 插值；两端直接取
  原桶值，得到的高度再夹到 0..满量程后从底部填充。
- 理由：`1/2/3` 的离散请求次数经过线性插值仍会在峰值处形成尖锐三角，和“最近两分钟请求密度”
  的连续观感不符。Catmull-Rom 在每个采样点有连续斜率，峰顶会自然变圆，同时仍穿过真实桶值。
- 后果：活动填充面的上沿随点列连续变化，仍使用同一块盲文画布与 60 秒网格；空窗口保持全空。
  新增端点、峰值和中点偏离线性的回归测试，文档同步为平滑插值。

## D49 流量曲线按 btop 滑动窗口连线，不再压缩完整 60 秒

- 问题：流量面板变窄后，代码仍把完整 120 个 0.5 秒桶映射到整个图宽。图只有几十个点列时，
  每个桶不足一个点，单个请求尖峰只剩一根细竖线；截图上看起来像停在图中部，而不是从最右侧
  出现后向左滚动。
- 决定：可见窗口按 btop net deque 的 `width*2` 样本语义处理：点列数少于 120 时只取最近
  点列数个桶（每个点列一个桶），点列数多于 120 时再拉伸填满完整窗口。最右侧始终是最新桶，
  历史桶向左移动。曲线改为在相邻采样点之间连线，不再从基线逐列填充。
- 决定：绘制前对上下行分别做 σ=2 桶的高斯平滑，并归一化回原始峰值；平滑只影响显示，不写回
  daemon 的桶、速率、Top/Total 或量程，避免尖峰被压矮。
- 理由：btop 绘制的是持续左移的采样曲线，不是把整个历史窗口压扁成静态柱面。dsmon 的流量
  又比 btop 稀疏，单桶尖峰必须保留可见的上升/下降沿，否则容易被误读为中线。
- 后果：`RenderTrafficNet` 新增窄窗截断、右对齐、连线和平滑逻辑；新增“最新桶贴右”“旧桶
  左移”“窄窗丢弃窗口外样本”“平滑保峰值”四组回归测试。

## D50 流量改为上下行各自基线做面积填充

- 问题：D49 把流量画成上下行两条细线，视觉上仍像“只画一个点”，和用户预期的 btop
  面积曲线不符；同时上下行共用同一条基线，和 btop 两个独立 Graph 的零线不一致。
- 决定：下载以中线最后一行点为零线向上填充，上传以中线后第一行为零线向下填充；每个点列
  从自己的基线填到平滑后的高度。上下行仍共用一块盲文画布，但各有自己的基线。
- 理由：用户要求“整条填充”和“上下行各画一条自己的基线”。面积填充也能让稀疏的代理流量
  在低矮面板里保持可读，不会退化成单个点或细线。
- 后果：`TestTrafficNetHasNoVerticalGrid` 改为断言两条零线；其他渲染测试继续排除基线行，
  只检查曲线高度列。滑动窗口、右对齐、显示平滑和独立量程均保持不变。

## D51 量程按十进制就近取整，统计子框边框改用 btop 灰色

- 问题：底层量程已经是 30K、100K、150K 这类十进制整档，但标签沿用 btop 的 1024 进制
  humanizer，显示成 29K、98K、146K；用户要求 98K/103K 显示 100K、147K 显示 150K、
  29K 显示 30K。
- 决定：量程改为按十进制就近取整：10K–100K 用 10K 步长，100K–1M 用 50K 步长；
  10K 以下保留 0.5K 粒度，M/G 档按同样比例放大。标签改用 1000 进制显示。
- 决定：流量面板右侧统计子框的边框改用 btop 当前主题 `div_line` 色 `#414868`，
  标题仍用 `title` 色，内容保持正常前景色。
- 理由：量程标签必须和实际柱高使用同一个数值，不能只把 100K 的标签写成 100K 而底层
  仍按 1024 进制画。子框灰边则直接对齐 btop `createBox` 的 `div_line` 语义；TUI 字符
  线宽无法变细，灰色是唯一可靠的“视觉变细”手段。
- 后果：`ScaleForPeak`、`NiceScale`、`NiceScaleBelow` 改用统一步长；棘轮升降档位随之
  变化，相关测试更新为 400K/350K/300K 等新档位。新增量程取整、十进制标签和灰边框回归测试。

## D52 上下行量程相差不到一倍时统一

- 问题：下载 60K、上传 70K 时两条半区的刻度不同，虽然都接近，但看起来像两套独立的图。
- 决定：在 daemon 的棘轮之后比较上下行量程；`max/min < 2` 时把两边都设为较大值，
  正好 2 倍或更远（如 50K/100K）保持独立。该判断用严格小于，避免浮点边界把“正好两倍”
  误合并。
- 理由：用户倾向“只要没有差一倍就统一”。这个规则简单、可预测，也不会把 50K/100K
  这种确实差一倍的场景强行拉平；比“相差一档”更不容易受 10K/50K 混合档位影响。
- 后果：`Trace` 的 `down_scale`/`up_scale` 在接近时相同；原始峰值、棘轮内部状态和
  daemon 桶不变。新增纯函数测试与 server 集成测试，覆盖 60K/70K 合并和 50K/100K 不合并。

## D53 活动移到账户行右侧，流量窗口延长到 120 秒

- 问题：活动与流量左右并排时，流量只能拿到半屏宽度；用户希望活动移到账户行右侧占 1/3，
  让流量独占下一整行，并把流量历史从 60 秒延长到 120 秒。
- 决定：内容宽度 ≥60 列时，账户占左侧 `width - 1 - width/3` 列，活动占右侧 `width/3`
  列，中间留 1 列并保持同高；流量在下一行占满宽度。更窄时回退为账户整行、活动/流量堆叠。
- 决定：流量采样保持 0.5 秒，桶数从 120 增到 240，窗口变为 120 秒；速率仍取最近 2 秒，
  量程棘轮、上下行合并规则和 Top/Total 口径不变。
- 理由：账户与活动都只需半屏高度，合并到首行后，流量可以用整行宽度展示更多盲文点列；
  延长历史时不降低采样密度，才能保留 btop 的点密度和单桶尖峰。
- 后果：daemon 与 TUI 帧中的流量桶数组长度变为 240。流量图宽度 ≥120 字符时显示完整
  120 秒；更窄时仍按 btop 的滑动窗口语义只显示最近一段，最右侧始终是最新桶。

## D54 活动曲线去掉竖向参考线

- 问题：活动图每 60 秒画一根贯穿画布的竖线，叠在盲文填充面上后会被误读成曲线的一部分。
- 决定：`RenderActivity` 只绘制平滑填充面，不再绘制时间竖网格；流量图的基线和填充逻辑不变。
- 理由：活动图的时间跨度只有 120 秒，满窗口内两根参考线提供的信息有限，却会打断曲线上沿的
  连续观感。用户需要看的是请求密度，而不是时间刻度。
- 后果：空窗口保持全空；新增零数据无竖线、单峰曲线仍能正常绘制的回归测试。历史决策中关于
  旧网格的描述保留不改。

## D55 流量曲线去掉显示平滑

- 问题：流量曲线此前对上下行桶做 σ=2 的高斯显示平滑，单桶尖峰会被摊到相邻点列，曲线更圆，
  但低流量时看起来不够锐利，也不容易判断尖峰具体落在哪个采样桶。
- 决定：`RenderTrafficNet` 直接使用 daemon 的 0.5 秒原始桶，每个桶画成从自身基线起算的
  竖线/面积柱；宽窗时重复最近的原始桶，不再做相邻桶线性插值。滑动窗口、右对齐、上下行
  独立基线、量程和速率逻辑不变。活动曲线保持 Catmull-Rom 平滑，不受影响。
- 理由：用户希望先观察不做显示处理的原始流量是否更清晰。去掉平滑后，单个请求的尖峰只占
  自己的点列，时间和高度对应关系更直接。
- 后果：删除 `smoothTrafficValues` 和对应测试；最新桶回归测试改为要求单桶只形成一条竖线，
  不再期待向左侧扩散的尾巴；新增宽窗原始桶重复、无插值斜坡的回归测试。

## D56 流量历史桶固定占一个点列

- 问题：宽窗时原始桶数量少于盲文点列数，D55 的最近桶重复策略会让同一个桶占 1 或 2 个
  点列；历史柱左移时，视觉上就在一条和两条竖线之间跳动。
- 决定：取消流量图的横向拉伸。每个桶固定映射到一个盲文点列；样本不足一屏时整体右对齐，
  左侧留空。窄窗仍只取最近 `width*2` 个桶。
- 理由：流量图首先要求同一个数据在移动过程中保持稳定宽度。右对齐与 btop 的 deque 行为
  一致，也避免拉伸产生虚假的宽度和时间跨度。
- 后果：宽窗左侧可能暂时留空，历史填满后自然向左延伸。新增宽窗单桶固定一列、连续 shift
  下竖线数量稳定的回归测试。

## D57 流量历史按画布宽度铺满，不再固定 120 秒

- 问题：固定保留 240 个 0.5 秒桶只能覆盖 120 秒。宽屏要么把桶拉伸到多个点列，导致同一个
  桶在一条和两条竖线之间跳动；要么右对齐留空，浪费画布宽度。
- 决定：daemon 保留最近 3600 个 0.5 秒桶（30 分钟）。IPC 根据 TUI 请求宽度只发送最近
  `width*2` 个桶；渲染仍保持一个桶对应一个盲文点列，不再拉伸。标题显示当前画布实际可见
  的秒数，例如图宽 170 字符显示 `流量 · 170 秒`。
- 理由：每个字符包含两个 0.5 秒点列，因此一个字符宽对应约 1 秒历史。让可见时间窗随画布
  宽度增长，既能把空间画满，也能保证每个桶的竖线宽度固定。
- 后果：IPC 不再每次传输完整的 3600 个桶，而是只传当前窗口；量程峰值也按可见窗口计算，
  不会被窗口外的旧尖峰抬高。窗口外的历史仍保留在内存中，终端变宽后会重新纳入显示。

## D58 模型发现路由透传但不写入用量

- 决定：仅放行 `GET/HEAD /v1/models` 与 `/v1/models/{id}`；按 `anthropic-version` /
  `x-api-key` 判定协议并选择 Anthropic base，其余请求走 OpenAI 兼容 base。未知辅助路径和
  `/v1/models` 的非只读方法仍返回 404。
- 理由：Codex doctor、OpenCode 等客户端需要模型发现来确认 provider 可用性；只放开这一组
  元数据路由可以修复探测，同时保持推理路由白名单，不把任意 `/v1/*` 请求暴露到上游。
- 后果：辅助路由复用现有鉴权改写、压缩、SSE 和并发限制，但不写 `usage_log`，因此模型统计、
  请求页和费用不会被探测请求污染。上游失败只保留在日志和 HTTP 响应中，不生成用量失败行。

## D59 请求上限抬到 50MiB，大图改走 Files API

- 问题：Codex 每轮 `/v1/responses` 都重发完整会话；几张 base64 截图就会把请求推过原来的
  20MiB 上限，客户端只看到本地代理返回的 413。DeepSeek 上游的请求体上限是 48MiB，且内联
  图片计入其中，单纯继续抬高本地上限仍然会撞上游。
- 决定：本地声明正文上限改为 50MiB；OpenAI 协议下请求超过 40MiB 时，识别 Responses
  `input_image`、Chat `image_url` 和 `file.file_data` 三种内联图片，按体积从大到小上传
  DeepSeek Files API，把成功的位置换成 `file_id`，目标降到 36MiB 以下。
- 决定：Files API 上传设置 30 天有效期和 60 秒总预算；`file_id` 只做内存缓存，缓存键包含
  提供商、key 指纹与图片 SHA-256。上游明确回 `file_id` 不存在/不属于当前账号时清掉对应条目。
- 决定：只有提供商为 `deepseek` 且使用 OpenAI 协议时启用；任何解析、上传或改写失败都原样
  转发，避免辅助优化把请求改坏。上传图片本体计入上行流量，主请求按改写后的实际体积计算。
- 后果：`internal/proxy` 新增 data URL 纯逻辑、multipart 上传端、缓存与编排；本地 413 文案
  显示 `50MiB`，上游 413 仍按上游响应透传并在日志里给出会话体积线索。

## D60 TUI 配色跟随 Omarchy 当前 btop 主题

- 问题：TUI 的边框、标题、状态色和曲线渐变此前写死为 Tokyo Night；用户切到 Ashfall 等
  Omarchy 主题后，btop 已换色，但仪表盘仍是旧配色。
- 决定：TUI 启动及每秒 tick 读取
  `~/.local/state/omarchy/current/theme/btop.theme`，把 btop 的 `main_fg`、`hi_fg`、
  `inactive_fg`、box 边框、`div_line`、温度/网络渐变映射到现有 tone；选中态使用
  `selected_fg` / `selected_bg`。若 btop 配置指定了自定义 `color_theme`，优先读取对应文件。
- 决定：解析失败或文件暂时缺失时保留当前 palette；首次启动没有主题文件才回退 Tokyo Night。
  主题切换不改 daemon、IPC 或数据库，只在下一帧重新渲染。
- 后果：TUI 的普通文字继续使用终端前景色，其余强调色、状态色、曲线渐变与当前 btop 主题一致；
  `NO_COLOR` / `--ascii` 行为不变。新增主题解析、字段映射、自定义 btop 主题和 tick 热更新测试。

## D61 余额 24h/7d 趋势保留完整时间轴

- 问题：下采样只在有采样或能向前填充的桶里输出点，TUI 又把这些点均匀铺满整行。实际只有
  最近 2 小时余额采样时，24h 会把这 2 小时拉满整行，7d 更会把单个点画成整行平线。
- 决定：`downsampleBalance` 在窗口内出现过采样后始终输出完整桶数；首个有效采样之前的桶标记
  为 `missing`，TUI 将这些时间桶留空。7d 只有最后一个 6 小时桶有数据时，只在最右侧显示
  对应一小段。
- 决定：`missing` 桶不参与 min/max、量程和颜色计算；完全没有采样的窗口仍返回空趋势。
- 后果：曲线横轴恢复真实时间比例，短历史不会被误认为持续了 24 小时或 7 天。新增 IPC
  完整窗口、TUI 左侧留空、缺失桶范围计算回归测试。

## D62 短历史余额趋势放大显示并标注真实覆盖

- 问题：严格保留 24h/7d 时间轴时，只有 2.5 小时采样会让 24h 只剩两个点、7d 只剩一个字符，
  虽然时间比例正确，但看不出余额变化。
- 决定：24h 下采样提高到 288 桶（5 分钟），7d 提高到 336 桶（30 分钟），保留短历史的细节。
  有效覆盖不足窗口 75% 时，TUI 把已有时间桶展开到整段 sparkline，并把标签改为
  `24h·2.5h` / `7d·2.5h`；覆盖达到 75% 后仍按真实时间轴绘制并留空缺失区间。
- 决定：覆盖时长由首尾有效时间桶和桶宽计算，不再依据请求数或估算值；完全没有有效桶时仍显示
  空趋势。
- 后果：新安装后的短历史既能看出形状，也不会冒充完整长窗口；数据积累满 18h（24h 视图）或
  5.25d（7d 视图）后自动切回真实时间轴。

## D63 活动曲线补上贯穿全宽的零基线

- 问题：活动图只绘制有请求高度的填充面，没有数据或有空桶时缺少水平参照，和流量图的基线
  语义不一致。
- 决定：`RenderActivity` 在盲文画布最底行逐点绘制零基线，贯穿完整画布宽度；数据填充仍从该
  基线向上生长。空闲、断线和时间桶全为零时基线保留。
- 后果：活动图与流量图共享同一种基线语言；ASCII 块字符回退不变。新增空活动、断线、单基线和
  无竖网格回归测试。

## D64 活动曲线按高度使用主题渐变

- 问题：活动图此前健康时整块只有单一绿色，峰值高度和普通高度在颜色上没有区别。
- 决定：健康状态下按画布行高映射主题 `temp_start → temp_mid → temp_end`，底部零基线为绿色，
  顶部满量程为红色；每个盲文行使用固定行色，形成和流量图一致的纵向渐变。异常/断线仍保持
  整块红色，避免把故障状态画成正常活动。
- 后果：活动峰值更容易从颜色上辨认，基线也随渐变着色；`--ascii` / `NO_COLOR` 仍保持单色
  回退。新增渐变端点和故障整块红色回归测试。

## D65 TUI 界面文案统一为英文

- 决定：`dsmon tui`、`dsmon settings`、余额/设置错误、客户端兜底名和 Omarchy 状态栏 tooltip
  全部使用英文；中文只保留在代码注释、维护文档和内部日志说明中。
- 决定：历史数据库里已有的中文客户端兜底名在渲染层映射为 `Unknown` / `Browser`，不改 schema，
  也不批量重写历史数据。
- 后果：英文列名和面板标题更宽，测试同步改为英文断言；40/80/200 列画布仍保持不重叠、不越界。

## D66 顶部导航改为单行快捷键导航

- 决定：第二行左侧显示全小写的 `overview usage requests pricing`，快捷键依次为
  `o/u/e/p`；激活页用方括号标记，快捷键字母使用当前主题强调色，其余文字固定白色。
- 决定：同一行右侧右对齐显示 `settings help quit`，快捷键依次为 `s/h/q`，同样只把键位
  字母着成强调色。宽度不足时优先保留页面导航，隐藏右侧操作文字。
- 决定：删除最底部常驻快捷键提示行，把新增的一行空间还给内容区；完整快捷键保留在帮助页。
- 后果：`o/u/e/p` 成为页面切换键，`h` 打开/关闭帮助，`s` 打开设置，`q` 退出；原有 Tab、
  方向键和数字区间快捷键继续保留。新增小写文案、强调色、右对齐和按键行为回归测试。

## D67 用量页区间角标与 series 稳定配色

- 决定：Query range 的六个区间文字改为白色，`1–6` 快捷键用强调色上标 `¹–⁶` 显示；激活区间
  仍用方括号标记，键盘输入保持数字键。
- 决定：维度切换显示为 `by [model] client`，`m/c` 使用强调色，当前维度加方括号；该选择从
  图表标题移到 Query range，系列详情标题只保留 `Series details`。
- 问题：用量柱体此前按纵轴高度做绿黄红渐变，同一高度行的不同 series 共用颜色，无法从柱段
  分辨模型或客户端。
- 决定：series 名按字典序稳定映射到当前主题的一组高对比颜色；堆叠柱段、图例点阵和系列名使用
  同一颜色映射，不再按高度着色。series 超过颜色数时循环复用。
- 后果：model/client 的堆叠颜色在刷新和排序变化时保持稳定；`--ascii` 回退仍使用点阵标记区分
  series。新增角标、维度选择、堆叠颜色和更新测试。

## D68 所有 codex 前缀客户端统一归为 codex

- 决定：`ClientFromUserAgent` 把以 `codex` 开头的客户端名统一归一化为 `codex`，覆盖
  `codex-tui`、`codex-exec`、`codex-cli`、`Codex Desktop` 等变体。
- 决定：`ClientRuleVersion` 提升到 3，启动维护重新推导有 UA 的历史行；同时把旧库中
  `Codex Desktop` 和 `codex-*` 的 client 值直接迁并为 `codex`，无 UA 的 `/responses` 历史
  也改推为 `codex`。`ClientInferenceVersion` 提升到 2。
- 后果：Usage 页的 client 分组不再把同一 Codex 客户端拆成多行；历史数据在 daemon 下次启动
  时自动合并，不需要手工改库。

## D69 版本号由 VERSION 文件维护并手动 bump

- 决定：`internal/version/VERSION` 是唯一版本源，通过 `go:embed` 注入 Go；TUI、设置页和
  `dsmon version` 读取同一个 `Current`。
- 决定：每次功能或修复修改完成后运行 `make bump-version`，默认只增加 patch。版本格式为
  `major.minor.patch`，每一位最大 99；patch/minor 溢出时向高位进位，`99.99.99` 拒绝继续递增。
- 理由：不能在每次 `make build/test` 时自动递增，否则开发过程中重复构建会让版本无意义地跳动；
  用显式 bump 让“一个修改对应一个版本”可控且可核对。
- 后果：当前版本从 `0.1.0-dev` 迁移为 `0.1.1`；新增版本格式测试和脚本边界验证。

## D70 流量桶宽与 TUI tick 改为 2 秒

- 决定：daemon 的流量采样桶从 0.5 秒改为 2 秒，TUI 的全局刷新 tick 从 1 秒改为 2 秒。
- 决定：速率仍使用 2 秒窗口，因此每次 TUI 刷新显示一个新流量桶，桶值本身就是最近 2 秒的累计。
- 后果：3600 个流量桶现在覆盖约 2 小时；流量图标题按每列 2 秒重新计算可见时间跨度，其余
  余额、请求和曲线数据也随 TUI tick 每 2 秒刷新一次。

## D71 活动曲线改为宽度驱动的 2 秒窗口

- 问题：活动曲线固定使用 20 个 6 秒桶，再把这些点拉伸到整个画布；和早期流量图一样，时间
  窗口由固定桶数决定，宽屏时无法用点列表达完整历史，曲线显得没有铺满。
- 决定：活动环改为 3600 个 2 秒桶，与流量采样和 TUI tick 对齐。TUI 只取面板点列数对应的
  最近桶，每个点列一个 2 秒样本，最新桶贴右；历史不足时右侧对齐，不再把少量固定样本拉伸。
- 决定：活动标题按面板宽度计算可见秒数；宽度足够时显示 `Activity · <n> sec · 3 req/cell`，
  窄屏退化为 `Activity · <n>s`。
- 后果：活动曲线和流量曲线采用相同的时间窗/点列语义；活动面板变宽会显示更长历史。新增
  默认桶参数、右侧对齐和动态标题测试。

## D72 TUI 顶栏移植工作状态图标动效

- 问题：macOS 版的菜单栏图标会随请求状态变化并持续动效；Linux 版此前只有静态
  `● Online`，缺少“刚有请求 / 刚闲下来 / 彻底空闲”的即时反馈。
- 决定：不移植 AppKit 菜单栏或 PNG 图标，在 TUI 顶栏原状态点位置做三档终端动效。请求发出
  后 10 秒显示仪表填充，先缓动升到满格再线性回落；随后 20 秒显示三格活动线，按 3 秒画出、
  2 秒淡出、5 秒循环；满 30 秒后回到静态月亮。离线、健康错误和余额错误继续优先覆盖工作态。
- 决定：daemon 的 `trace` 响应增加 `last_activity_unix_nano`，在请求发出时记录，只读暴露给
  TUI；数据库 schema、IPC 命令和 2 秒数据刷新不变。
- 决定：动画只在仪表或活动线档位启动 10Hz tick，空闲和错误态停止；颜色使用当前 btop 主题，
  `--ascii` / `NO_COLOR` 使用等宽 ASCII 字符。
- 后果：这是 D4“不做图标动画”在 Linux TUI 上的限定调整，不恢复 macOS 菜单栏、刘海、呼吸灯
  或报警等级。新增纯时间轴测试、状态优先级测试、ASCII 宽度测试和跨层最后活动时间测试。

## D73 Omarchy 顶部栏改为常驻工作状态图标

- 问题：D29 的 `cherno.dsmon` 只是点击打开 TUI 的静态入口，关闭 TUI 后看不到代理是否在跑、
  是否刚有请求、余额或 daemon 是否异常；TUI 空闲和离线时也缺少足够明显的状态动效。
- 决定：新增只读命令 `dsmon status --json`，从现有 `stats` / `trace` IPC 组合出
  `online`、健康、余额错误、今日请求/费用、最后活动和 daemon 当前时间。JSON 不包含 key、
  Authorization、正文或原始上游错误文本。
- 决定：Omarchy bar-widget 每 2 秒轮询该命令并在 QML 本地按 10Hz 绘制状态：请求后 10 秒为
  动态仪表，随后 20 秒为脉冲活动线，之后为月亮；daemon 离线或健康错误时红色慢闪，余额错误
  时黄色慢闪。点击仍打开或聚焦 TUI。
- 决定：TUI 顶栏同步补齐可见性：空闲月亮每 10 秒闪两下星，离线/健康错误红色慢闪，余额错误
  黄色慢闪；活动态仍为 10Hz，空闲态降到 4Hz，错误态降到 2Hz，避免无意义高频全屏重绘。
- 决定：QML 验证并限制所有数值范围，只把本地常量文案渲染为 PlainText；`Style.reduceMotion`
  开启时保留状态颜色和静态图标，停止持续动效。
- 后果：D29 的“只在栏内做启动入口、不显示实时状态”被本条目取代。仍需 daemon 运行才能得到
  实时状态；daemon 停止时栏图标会明确显示离线，而不是消失或伪装成空闲。

## D74 TUI 图标恢复静态，Omarchy 栏按 Mac 原版复刻

- 问题：D72/D73 未经确认把 Mac 版五格图标简化成终端字符仪表和三柱图；用户明确要求 TUI
  不显示图标动效，只用 Omarchy 顶部栏承载状态反馈。
- 决定：删除 TUI 的状态动画 tick、字符时间轴和全部空闲/错误动效，恢复静态

- 决定：Omarchy 插件直接使用 Mac 源仓库的 `menu_icon_*.png`，包括警笛、警告、月亮、月亮星、
  仪表盘和指针；活动线与指针由 QML 按 Mac 时间轴绘制。
- 决定：复刻五格传送带 `siren → warning → moon → trace → gauge`。每格滑动 0.45 秒并使用
  smoothstep；请求后 10 秒停仪表，之后 20 秒停活动线，再回月亮。仪表指针 0.4 秒扫到顶后

- 决定：离线、健康错误、余额错误或低于余额阈值都进入红色 siren 档并按 0.6 秒方波闪烁；
  warning 档保留在传送带中供后续告警来源使用。
- 后果：TUI 不再承担图标状态动效；关闭 TUI 后仍可从 Omarchy 顶部栏看到状态。Omarchy 的
  “减弱动态效果”设置开启时直接停到目标格并显示静态完整图标。

## D75 Omarchy 栏去掉活动线与月亮

- 问题：用户不需要 Omarchy 栏里的活动线和月亮星闪；无请求时停留在这两档反而不如直接显示

- 决定：请求后 10 秒内仪表指针按年龄扫动并回落；无论当前是否仍在 10 秒窗口，无请求时指针

- 后果：Omarchy 栏只承担告警与用量节奏反馈；warning 格仍保留在滑动路径中，供后续告警来源

## D76 Omarchy 仪表颜色按空闲时长分级

- 决定：最后一次请求后的 25 秒内，仪表盘和指针使用绿色 `#9ece6a`。其中前 10 秒是指针扫动

- 决定：距最后请求满 25 秒后，仪表盘和指针恢复当前 Omarchy 栏前景色；无请求历史时直接使用
  前景色和左侧低点。
- 后果：绿色表示“刚刚有活动”，白色表示“已经空闲”；颜色切换不改变三格报警/警告/仪表

## D77 Omarchy 活动色跟随主题强调色

- 问题：D76 固定使用绿色 `#9ece6a`，不会随 Omarchy 主题切换，当前 Ashfall 等主题下与其他
  界面元素的语义色不一致。
- 决定：最后活动 25 秒内使用 `Commons.Color.accent`，满 25 秒后恢复当前栏前景色。
- 后果：仪表活动色自动跟随主题强调色；当前主题的强调色可能是橙色，不强制为绿色。

## D78 仪表活动包含请求与上下行流量

- 决定：daemon 的最近活动时间不仅由请求发出刷新，非零上传字节和非零下载字节也刷新；零字节
  不刷新。活动曲线仍只按请求数计数，流量曲线保持原语义。
- 决定：Omarchy 仪表改为状态式指针。发现新的最近活动时间时，从当前指针角度开始 0.4 秒
  smoothstep 上扫，而不是先归零；截止时间更新为最新活动时间 + 10 秒。
- 决定：回落期间出现新活动时，从当时角度重新上扫；上升期间出现新活动也重新从当前角度起扫。
  持续上下行会让截止时间反复后移，指针会周期性上扫并维持高位。
- 后果：连续 SSE 下载、长请求上传和短时间多次请求都会维持绿色仪表；最后一次活动满 10 秒后
  指针落底，满 25 秒后仪表恢复主题前景色。

## D79 图片卸载路由先按 128MiB 接包再执行降体

- 问题：D59 把普通请求上限设为 50MiB，但图片只在 40MiB 以上才尝试卸载。长会话每轮重发
  历史图片，请求一旦越过 50MiB 就会在读包阶段被拒，图片卸载逻辑完全没有机会运行。
- 决定：仅对 `provider_id=deepseek`、OpenAI 协议且已配置 key 的图片卸载路由，把接包上限
  提高到 128MiB；普通路由继续使用 50MiB。卸载、上传或改写后，正文仍须小于等于 50MiB，
  否则本地返回 413。
- 理由：长会话必须先容纳超过普通上限的原始图片，才能上传并替换为 `file_id`；128MiB 给
  多张历史截图留出余量，同时仍给单次请求的 JSON 解码和内存使用设硬边界。
- 后果：本地 413 不再在可处理的图片请求上图先拦截；无图片的超大请求、上传失败且未降体、
  或改写后仍超限的请求仍会在本地被明确拒绝并记录大小。

## D80 Omarchy 仪表对齐 Mac 的暖光与空闲轻抬

- 问题：D77/D78 使用主题强调色覆盖仪表盘和指针 25 秒，且指针扫过 270°；Mac 版最终改为
  表盘始终黑白、活动只点亮圆弧内部，并增加空闲轻抬。两端的节奏和视觉语义已经不一致。
- 决定：指针改为从左侧低点到右侧高点扫过 240°；仪表盘和指针始终使用当前栏前景色。
- 决定：活动时在仪表圆弧内部绘制暖橙径向光，亮度与扩散直接跟随指针高度，指针落底立即
  熄灭。深色栏使用 `#ff9445`，浅色栏使用 `#c44a00`，按栏背景亮度选择。
- 决定：辉光中心峰值不透明度限制为 60%，中层为 34%，确保白色指针在橙色峰值时仍清晰
  可辨。
- 决定：完全空闲后随机等待 25–45 秒，指针以双拍轻抬 16°，总时长约 1.12 秒；有活动、
  告警、图标隐藏或 `Style.reduceMotion` 时立即取消并清空排期。
- 决定：平时按 10Hz 刷新，仅在滑动、指针上升或空闲轻抬时提升到 30Hz，避免空闲时持续
  高频重绘。
- 后果：D77 的主题强调色活动态和 D78 的 25 秒颜色尾段被本条目取代；请求与上下行流量
  继续刷新活动时间，三格告警/警告/仪表传送带不变。

## D81 Omarchy 右上活动卡片是 Linux 专属可选 UI

- 问题：Mac 版有刘海区域承载实时活动信息，但 Linux 版明确不恢复 Mac 刘海；用户仍希望
  在不打开 TUI 时看到最近一次请求的完整快照。
- 决定：新增可选的 Omarchy layer-shell 活动卡片，固定从当前屏幕右侧上沿、顶栏下方弹出，
  不占用工作区，不抢键盘焦点，mask 为空，所有点击继续落到桌面。

  曲线；两条曲线复用 TUI 的 2 秒桶、量程和 btop 主题渐变，只做紧凑绘制。
- 决定：卡片由 TUI settings 的 `Activity card` 开关控制，配置键为 `[ui] activity_card`；

- 决定：插件的 service 实例统一轮询 `dsmon status --json`，栏图标从同一实例读状态，避免

## D82 活动浮层改为 Mac 侧边刘海式竖条

## D83 活动竖条常驻缩边并支持悬停呼出

- 问题：活动结束就把竖条完全收起，用户无法主动查看余额和历史曲线；顶部状态灯又占掉了一整
  行，和 Mac 版侧边刘海的信息密度不一致。
- 决定：删除顶部状态灯，余额直接作为第一项。竖条不再在空闲时关闭，而是向右滑出屏幕，只在
  右侧保留 5px 的可见残边；鼠标进入这条残边时滑出，移开且没有新活动时重新缩回。
- 决定：layer-shell 的输入区域只覆盖可见卡片，缩回后就是那 5px；不再使用空 mask，因为
  Quickshell 的 `HoverHandler` 需要 visible card 在输入区域内才能接收鼠标悬停。
- 后果：活动触发和 10 秒 hold 仍然保留；新增的 5px 残边是获得悬停能力的必要输入区域，屏幕
  其余部分不受影响。关闭 `[ui] activity_card` 时整个竖条和残边都消失。

## D84 活动竖条曲线改为固定时间槽并按快照相位滚动

- 问题：竖条把 `dsmon status` 返回的 160 个 2 秒桶压缩进约 64px 的内容宽度。每次新桶到来，
  整条历史都要重新采样，Catmull-Rom / 线性插值会让同一个历史峰在像素网格上反复改变形状；
  同时 QML 没有使用桶相位，历史看起来像在持续抖动。流量图虽然解析了 `traffic_shift`，但
  从未传给绘制层。
- 决定：活动曲线和流量曲线都改为一个 CSS 像素固定对应一个桶，只画当前宽度装得下的最近桶；
  样本不足时右对齐，左侧留空。相位从承载数据快照的 `server_now_unix_ms` 开始累计，允许
  超过 1；下一次快照到达时数组左移、相位回绕，两者抵消，因此两次快照之间不会回跳。
- 决定：流量曲线不再使用 daemon 按 160 点宽计算的 `traffic_shift`，改由 QML 按卡片实际
  像素宽度重算相位；daemon 的 IPC 字段和 TUI 行为保持不变。
- 理由：历史曲线的横向位置必须只由时间决定。把数组拉伸到画布宽度再逐帧重采样，会让同一段
  历史在视觉上“变形”；固定槽位后，历史峰只随时间平滑左移。
- 后果：卡片内容宽约 64px 时显示最近约 128 秒，而不是原来的 320 秒；这与 Mac 侧边刘海的
  2 分钟窗口同量级。流量量程仍沿用 daemon 的棘轮，所以涨档/降档时峰高会整体缩放，但时间轴
  不再重排。

## D85 TUI 活动曲线相位方向修正

- 问题：`RenderActivity` 用 `x - offset - phase` 计算采样位置，相位增大时历史峰实际向右
  移动，跨过桶边界后再跳回左侧；这和 Mac `ActivityCurveRenderer`（`slot * i - shift`）以及
  `docs/CURVES.md` 的“历史左移”相反。
- 决定：改为 `x - offset + phase`，并新增方向性回归测试：同一个峰在 3/4 桶相位时必须位于
  桶边界相位的左侧。
- 后果：TUI 活动曲线在两次刷新之间向左平滑爬动，跨桶不再反向跳动；流量曲线本来就用
  `x - offset + shift`，不受影响。

## D86 活动竖条去掉右缘描边并独立滑入滑出

- 问题：`NotchSurface` 的描边路径 `closePath` 会在屏幕右缘画一条竖线，导致卡片和黑色屏幕
  边之间出现可见接缝。另一方面，本机 Hyprland `animations:enabled=false` 会让 Omarchy 的
  `Style.reduceMotion=true`，原来的 `Behavior on x` 被禁用、`Style.duration()` 也返回 0，
  卡片开合变成瞬移。
- 决定：填充路径仍闭合到右缘，但描边改为不 `closePath` 的开放路径，只保留上下凹角和左侧
  边框，不再描右缘竖线。
- 决定：卡片显隐改用独立的 `cardRevealWidth`（0 / 5px / 88px），用固定 190ms 的
  `NumberAnimation`。这条竖条的滑动不再跟随 `Style.reduceMotion`；其他 shell 动画不变。
- 决定：层表面首次映射时以 0 可见宽度放在屏幕外，下一拍再滑入；关闭时先滑到 0，等动画结束
  后再隐藏 layer surface，避免突然出现或关闭。
- 后果：卡片右缘与屏幕黑边融合；活动、悬停、禁用和离线切换都会连续滑入滑出。`Hyprland
  animations:enabled=false` 时，这条竖条仍保留自己的滑动语义。

## D87 活动竖条使用 12px 主数值并整体收紧

- 问题：本机 shell 的 `base-size = 14` 让活动竖条主数值达到 16px、标签达到 12px，竖条在
  右上角显得过大；今日费用还保留四位小数，宽度和精度都超出日常查看需要。
- 决定：主数值固定为 12px；标签和图表标题沿用 shell 的 `caption / title` 比例，当前为 9px。
  卡片宽度、内边距、行高、图表高度和凹角按原尺寸的 0.75 收紧。
- 决定：右侧悬停残边继续保持 5px，不随卡片缩放；今日费用改为两位小数。
- 后果：竖条约从 103×483 缩到 77×362，信息层级不变但更紧凑；字号不再随主数值继承
  `Style.font.title`，避免本机更大的 shell 字号把卡片撑开。

## D88 活动竖条优先展示请求曲线

- 问题：请求曲线放在五项指标之后，需要向下扫过整张竖条才能看到最近请求趋势；同时请求区
  与流量区高度接近，在窄卡片里挤占了指标空间。
- 决定：请求曲线移到卡片第一项；请求绘图区高度固定为流量绘图区的一半。
- 后果：卡片总高度再减少约 6px，最先看到的是请求趋势，指标和流量曲线依次排在下面。

## D89 活动竖条跟随系统窗口圆角与透明度

- 问题：活动竖条使用自己的固定圆角和完全不透明底色，主题调整 Hyprland 的窗口圆角或
  不透明度后，浮层仍和普通窗口的观感不一致。
- 决定：左缘普通圆角直接使用 `Style.cornerRadius`（来自 `decoration:rounding`）；整张卡片
  使用 `decoration:inactive_opacity`，因为它是不可聚焦的被动浮层。配置重载时重新读取。
- 后果：贴右屏幕的凹口仍是固定刘海形状，不随窗口圆角放大；系统窗口透明度变化会同时作用
  到卡片底色、文字、曲线和边框。

## D90 活动竖条贴屏幕边缘的凹角也跟随系统圆角

- 问题：D89 只让卡片左缘使用系统窗口圆角，右侧贴屏幕边缘的上下凹角仍固定为 6px；系统改成
  直角或更大圆角时，卡片两侧的弧度不一致。
- 决定：右侧凹角的 `flare` 同样使用 `Style.cornerRadius`，系统圆角为 0 时退化为直角。
- 后果：卡片四个视觉边角统一跟随 Hyprland 的 `decoration:rounding`；右缘仍不留竖线，并保持
  贴屏幕边缘的刘海轮廓。

## D91 活动竖条 hover 边框复用活动窗口边框

- 问题：活动竖条始终使用 Hyprland inactive border，鼠标悬停后仍像未聚焦窗口，和当前主题
  中活动窗口的边框语义不一致。
- 决定：`cardHovered` 为真时使用 `Border.hyprlandActiveSpec()`，绘制与 Omarchy 活动窗口
  相同的纯色或渐变颜色及角度；鼠标移出后立即恢复 inactive border。
- 后果：悬停状态自动跟随当前 shell 主题的活动边框 token，不需要额外轮询 `hyprctl`；
  未悬停时仍读取实时 inactive border。
